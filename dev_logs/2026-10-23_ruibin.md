## 3. Technical Details and Decisions

### 3.1. Spark TUN and DU console changes

| Role | Spark service address / TUN | Radio observed in retained startup |
| --- | --- | --- |
| UE1 / DU1 | `10.45.0.1 / ogstun_1`, DNN `internet` | n78, 3660 MHz, PCI 1, B210 `3271233` |
| UE2 / DU2 | `10.46.0.1 / ogstun_2`, DNN `internet2` | n78, 3600 MHz, PCI 2, B210 `328B021` |

Both TUNs retained the shared UPF. IPv6 `2001:db8:cafe::1/48` stayed on
`ogstun_1`. This separated Linux interfaces without creating two independent
Core stacks. The migration bundle retained its original/prepared files and
rollback procedure; its 15 archived file checksums passed.

The console launcher used util-linux `script` with output-only logging and
kept sudo inside a terminal. The earlier foreground-process-group problem
prevented DU stdin from receiving interactive commands. The command dispatcher
also treated semicolons as separators, so the handbook documented commands
such as `;h;` and `;rx_gain 0 30;`. DU2's actual transcript confirmed help and
three successful gain changes; its last recorded acknowledgment was 15 dB.
The gain commands had no individual timestamps, so their causal relationship
to the MPTCP path events was not established. A live DU1 help/gain response was
not recorded, although its PTY startup, logging and clean exit were retained.

The server resolved config selected backend `mptcp`, TCP data port `9001`,
UDP control port `9002`, and listen addresses `10.45.0.1 / 10.46.0.1`.
The audited session was `3d293a88328ef4b45294ee09cd7d3d28`. All **1,197** retained
metrics records from **19:32:00.076518–19:33:59.905782 EDT** contained these two
established MPTCP subflows:

| Dashboard path | Role | Server ↔ UE address pair |
| --- | --- | --- |
| Path 1 / link-1 / “FR1” | Backup | `10.45.0.1 ↔ 10.45.0.3` |
| Path 2 / link-2 / “FR3” | Primary | `10.46.0.1 ↔ 10.46.0.4` |

Both paths showed positive received-byte growth. Server events recorded
link-2 degraded at **19:33:04.278661**, down at **19:33:04.678671**, and up at

to Path 2. This established functional primary/backup MPTCP video operation;
simultaneous bandwidth aggregation and a precise failover latency were not
measured. The exact fault-injection method was not recorded.

### 3.3. Laptop routing/reset design — live validation pending

The operator's UE1 transcript lacked destination-only priorities `10153/10154`,
while source-bound lookup used table 151. The missing destination rules allowed
ordinary traffic to fall through to the Wi-Fi main route.

The revised handbook installed `to 10.45.0.1/32 unreachable` at priority `20151`
for UE1 and `to 10.46.0.1/32 unreachable` at priority `20152` for UE2 **before**
reset. These independent rules survived cleanup of the normal role priorities
and preceded the main table's priority `32766`. Rebuilding installed both source
and destination lookups/guards at `10151–10154` or `10161–10164`.

After a guarded reset, ordinary ping and TCP/UDP to the affected service IP
were expected to fail until rebuilding completed; other destinations retained
Wi-Fi management access. The blocks also remained after shutdown, but required
reinstallation after a laptop reboot. The underlying reset helper was unchanged;
the handbook's guarded sequence was required to install the extra blocks.
This design was not applied to or validated on the UE laptop during this work.
