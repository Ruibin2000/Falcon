## 3. Technical Details and Decisions

### 3.1. Active implementation and repository scope

The active path used the native C E2 collector and the Python coordinator,
matcher and broker. The operator chose to retain Python for this extension.
The accepted identity path continued to join CU E2 identity with Open5GS
AMF/SMF infoAPI context to obtain NGAP/SUPI/session/DNN/current IPv4 information.
MPTCP consumers needed the resulting IP-to-KPM correspondence rather than
another Core or E2 client.

FlexRIC `d93076ee` committed the separate standalone C base5 broker example
and its build/fixture support. That historical prototype was not the live
27-metric Python v2 publisher. The active path reused the retained SDK and
isolated KPM plugin; the FlexRIC commit added no SDK-core change. OCUDU stayed
on `falcon-dev` at October 25 commit `9bbf639850`; no new OCUDU source commit
was recorded for today's subscription extension.

### 3.2. Protocol and lifecycle

- The endpoint was `127.0.0.1:8765`, with protocol version 2, profile
  `du27_bound_v1`, and one UTF-8 JSON object plus LF per frame.
- Registration established an actual callback-entry cutoff before delivery.
  Full radio keys distinguished equal F1AP numbers on different DUs. Snapshots
  retained their association at generation instead of consulting a newer IP
  when the socket eventually wrote the report.
- New matched DU reports drove publication at nominal 100 ms per link; no
  additional periodic replay timer was added. CU identity and Core polling
  remained at 1000 ms, with the configured 3-second source TTL.
- Clients sent heartbeat every 10 seconds. Default registration/incomplete
  deadlines were 5 seconds, request idle expiry 30 seconds, pending writes
  without progress 5 seconds, and unregister/shutdown drain at most 2 seconds.
- Ingress was bounded at 256 reports / 4 MiB and each client output at
  64 frames / 1 MiB. Application disconnect/reconnect did not add E2 subscriptions.
  Reconnection required a new TCP registration and provided no historical replay.
- The first paced run exposed suppression of the last fresh queued report
  when source EOF changed state. Publication ordering was corrected so fresh
  snapshots preceded state notices; a dedicated barrier regression passed.

### 3.3. Application association and interpretation

The client read IP from `report.ue_ipv4`, node identity from `report.node`,
UE identity from `report.row.ue`, and measurements from `report.row.metrics`.
MPTCP was expected to match the report's UE source IP against its own current
path/address table and keep per-link freshness and provenance. Broker/session
IDs and decimal-string sequences were explicitly distinct from stable MPTCP
path or subflow identities.

Valid zero, signed REAL values and `no_value` remained distinct. The two
HARQ/CRC percentages stayed separate derived values. A 100 ms report period
did not imply a new observation for every field: PHR/BSR/Buffer age fields
could reach several seconds. A healthy pong or one active UE stream did not
establish freshness for the other path. These semantics and the v1-to-v2
field/name changes were included in the MPTCP interface document.
