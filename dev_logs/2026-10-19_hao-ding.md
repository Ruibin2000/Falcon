### Step 2 measurement semantics

The committed note traced RSRP and SINR through PHY estimation, FAPI conversion, MAC handling, scheduler accumulation, and KPM access.

- RSRP represented software uplink DMRS power in dBFS. The vendor SNR measurement exposed the selected PHY SINR estimate.
- Source/configuration inspection indicated the default `post_equalization` estimator. This was an inference from the inspected code and configuration, without runtime verification.
- Conversion saturated RSRP to `[-128, 0]` dBFS and SINR to `[-65.534, 65.534]` dB. Quantization steps were 0.1 dB and 0.002 dB, using truncation.
- Missing-value sentinels were distinct from measured zero. Scheduler averages included available RF samples from failed-CRC reports.
- Scheduler windows independently averaged available dB samples. Missing RSRP used negative infinity; missing SNR could appear as zero, requiring a positive SNR report count to establish validity.
- Upstream saturation could already turn an infinite estimator result into a finite endpoint; the KPM provider could not reconstruct the original pre-clamp value.

The required KPM contract remained UE-level `FALCON.PUSCH.RSRP.dBFS` and `FALCON.PUSCH.SNR.dB`, encoded as REAL, with exactly one `NO_LABEL`. Missing/non-finite values require `noValue`; measured zero remains valid. SNR additionally requires `nof_pusch_snr_reports > 0`. Each requested UE requires one record in request order, using F1AP translation followed by lookup by `ue_index`.

### Step 3 findings and pending Plan A decision

Static review found the candidate already contained UE translation and `ue_index` lookup, request-order/cardinality handling, REAL/noValue handling, valid-zero handling, SNR sample-count checks, label/scope restrictions, and vendor registrations. Fresh acceptance tests and production capability decoding remained pending.

The candidate lacked synchronization across mutable provider caches and lacked snapshot-generation support.

The inspected executor model showed:

- Scheduler/RLC metrics reached the provider through a distinct metrics strand.
- DU control, F1AP, and E2 timers shared one control strand.
- E2 receive processing used the raw thread-pool executor.
- Subscription deletion could resume a suspended indication coroutine inline, allowing final collection on the receive path.

These were static findings; no runtime concurrency failure was reproduced.

Design A proposed one mutex covering scheduler snapshots, associated counts, RLC cache/history, cleanup timing, and affected readers. Snapshot generation and metadata would be published in the same critical section. F1AP-dependent cleanup would move to control-strand E2 read entry points.

A separate prerequisite patch would change `apps/du/du.cpp` to route E2 receive through `du_e2_executor()`. This would move receive/decode work onto the control strand and require queue-delay, ordering, and later runtime-load validation. Cleanup would also be deferred while no E2 reads occurred, requiring retained-cache review.

**Design A was not approved.** The user planned to discuss it with the project lead/reviewer, particularly the `du.cpp` change and its trade-offs. A safe variant without that change had not been designed or approved. The document’s Alternative B also required E2 receive confinement.
