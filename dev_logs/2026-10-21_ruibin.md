## 1. Daily Summary

Implemented **dual-UE link-to-IP association on the xApp side**. Extended
OCUDU CU-CP identity collection and CU E2 reporting, built a standalone xApp
that subscribed to CU/DU1/DU2 through FlexRIC, and queried the existing
Open5GS AMF/SMF interfaces to associate radio identities with actual subscriber,
session and IPv4 information. The application emitted the combined identities,
UE IP and original KPM as pure xApp TXT and NDJSON output.

Real dual-UE validation passed in two scenarios. Simultaneous 60-second TCP
uploads achieved receiver throughput of **13.2 Mbit/s for UE1 and 11.9 Mbit/s
for UE2**, with both clients exiting 0; the associated 120-second xApp capture
had **221 matched / 223 records**. A subsequent 360-second bidirectional
idle/resume capture had **645 matched / 648 records, zero cached**, with both
UEs retaining their IPs after radio-context changes. During each UE's actual
Core idle interval, its active peer retained **30 consecutive matched
positive-UL records**. All four dynamic-test clients and the xApp exited 0.

The completed checkpoint was **CU Identity E2 Reporting Passed / Dual-UE
IP-KPM Association Passed / Bidirectional Independent Idle-Resume Passed** in
the tested observational lab mode. Initial scope and strict serving-DU/context
generation, exact reuse, restart/recovery and cold-start reproduction remained
open. Plan 2 broker and MPTCP/MPX integration remained separate. Preparing this
log reran file-only audits and software tests; it did not rerun a hardware
experiment or start/restart deployed services.

## 3. Technical Details and Decisions

### 3.1. Information sources and matching keys

| Source | Information used |
| --- | --- |
| DU E2 | PLMN/gNB/DU node identity, gNB-CU UE F1AP ID, original five KPM metrics and measurement metadata. |
| CU E2 | AMF UE NGAP ID, GUAMI, CU UE F1AP ID list and RRC state. The local getter also reads serving-DU context. |
| AMF infoAPI | SUPI, AMF/RAN UE NGAP IDs, gNB identity, connection state and reported cell/NCI. |
| SMF infoAPI | SUPI, PDU Session ID, DNN, UE IPv4 and session state. |

The implemented join was **DU/F1 → CU scoped NGAP/GUAMI → AMF SUPI → SMF
session/IP**, followed by attaching the identity/IP fields to each original
DU KPM row. GUAMI endpoint scope was explicit configuration. F1 and NGAP
numbers were typed identifiers; numeric equality and IP subnet inference were
not association rules. Laptop IMEI/IMSI/bearer/source-IP records provided
independent validation evidence.

The CU read its local contexts; the xApp queried
`http://127.0.0.5:9090/ue-info` and `http://127.0.0.4:9090/pdu-info`.
Core source, subscriber/IP allocation and session policies were unchanged.
The CU identity collection was enabled with `metrics.layers.enable_ue_identity`.
The CU report period and xApp polling period were one second, with a
three-second freshness TTL.

### 3.2. Current association and historical fallback

The live dynamic test used `independent_links: true` and
`--observed-unique --fresh-only`. It disabled historical IP fallback while
retaining established radio scope. The active peer remained `matched` using
fresh own CU/Core inputs when the other DU became stale. Across the dynamic
capture, 59 records exercised `established_du_scope_current_context`.

Normal `last_known` mode could reuse a context's verified history when that
UE's own verification inputs were missing, explicitly labelled `cached` with
last verification time and age. This policy was covered by software tests;
zero cached records in the accepted live run proved current association for
that run. Known conflicts, retirement and input loss invalidated confidence.
New contexts did not inherit unrelated or retired IP history.

The current standard CU UEID did not transport an explicit per-UE serving-DU
ID or a shared CU/DU generation. Initial experimental scope establishment
therefore required all admitted DU sources to be current and observed
candidates to be unique. Default strict mode withheld IP publication. The
validated live association did not close those stricter transport/lifecycle
gates.

inputs in `inputs.ndjson`, and associated rows in `rows.ndjson`.
